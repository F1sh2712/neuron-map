## 技术难点与决策

### 1. PDF vs Markdown：为什么最终选 Markdown-first

先做了 PDF 原生提取原型（Claude 直接读 PDF，能读图），跑通并测试过。但在成本和准确度分析后转向 Markdown：

- **成本**：一份 50 页课件，PDF 原生方案约 $0.31（图片 token 占大头），本地文本方案几乎为零
- **准确度**：`.md` 的 `#`/`##`/`###` 是**语义标题**，可以确定性地映射成 star / planet / asteroid，最可靠；PDF 里标题只是「字大一点」，代码提取不到可靠层级
- **可验证**：Markdown 是可看可改的中间产物，验证提取质量容易

结论：Markdown 是「便宜 + 确定 + 层级可靠」三者都成立的甜点区。PDF 原生代码保留，作为未来的适配器。

### 2. 研究 Resume-Matcher 作为参考架构

研究了 GitHub 上知名的 Resume-Matcher，学到几个关键点：

- 它本质是 **AI 工作流（workflow）**，不是自主 agent——所有编排都是普通代码写死的，LLM 只当「文本 → 结构化 JSON」的转换引擎。我们现在的做法一致，这是正道
- 它用 `markitdown` 库把 PDF **零成本**转成 markdown（纯代码，不花 token），印证了「代码解析 PDF→MD」路线可行
- **它砍掉了 embeddings**，简历匹配改用纯代码关键词打分——说明向量搜索不是必需品，别过度设计。我们的 pgvector 也应推迟到真正需要跨文档搜索时

### 3. 代码全面英文化

为匹配澳洲求职，把整个代码库（UI 文字、注释、prompt、报错、commit）统一改成英文，并把这条规范写进 CLAUDE.md、AGENTS.md、review checklist 三处，确保不再写回中文。交流仍用中文。

### 4. 宇宙图谱渲染器

自定义 Canvas + `requestAnimationFrame`：恒星锚定，行星绕恒星、陨石绕行星做轨道运动。踩了两个坑：

- **TypeScript 闭包窄化**：`if (!canvas) return` 的非空窄化不会带进嵌套函数闭包，`next build` 真的报错。用非空断言解决
- **点击重转 bug**：主 useEffect 依赖里带了 `selected`，每次点击都重建整个星系。改成用 ref 读取选中状态修复

交互做了：拖拽后自动**重新归属最近的更大天体**并继续绕转（拖陨石到别的行星旁边就改绕那颗）、点击弹详情面板、悬停高亮。

### 5. 用设计工具探索「技能树」学习视图

意识到宇宙图谱擅长展示层级、但不擅长清晰展示「两个知识怎么连」，于是探索用**技能树**（Diablo / 科技树）作为更清晰的学习视图。用设计工具做了两轮设计稿：第一轮踩了「AI 味」审美的雷（深色 + 发光 + 紫青渐变），第二轮换成三种真实设计流派（Swiss 国际主义 / 古星图铜版画 / 地铁线路图），方向已确定。

## 遇到的问题

### 问题 1：澳洲 Wi-Fi 不稳导致 GitHub 推送和 Supabase 认证间歇性失败

多次 `git push` 报 `Failed to connect to github.com port 443`，以及上传页因 `proxy.ts` 调 Supabase 验证登录而卡 30 秒超时。诊断确认是**网络问题，不是代码/账号问题**（curl 测 GitHub/Supabase 返回 000 超时）。重连 Wi-Fi 后恢复。教训：看到 `port 443 timeout` 就是网络,等一下重试即可。

### 问题 2：设计稿第一版「太 AI」

第一轮技能树设计稿套用了默认的深色发光渐变审美，被指出「太 AI」。反思：这正是设计准则里明确要避免的 AI-slop 套路。第二轮改用有明确流派归属的设计语言（浅色有质感的底 + 特征字体 + 平面/线条而非发光），问题解决。审美需要来回打磨，不能套默认。
