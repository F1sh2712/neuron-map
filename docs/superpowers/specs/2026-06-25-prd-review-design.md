## 说明

本文档记录对 NeuronMap Phase 1 PRD 的全面审查结果，共发现 19 条问题。  
**不修改 PRD 原文**，由开发者决定哪些进 Phase 1、哪些进 backlog。

---

## Section 1 · 用户旅程断层（4 条）

### 🔴 S1-1 · 提取失败后文档永远卡在"处理中"

PRD F3/F4 只描述成功路径。Claude API 中途报错（超时、rate limit、非 JSON 响应）时，`Document.status` 停在 `PROCESSING`，用户看到进度条停止，无重试入口，无错误提示。

**缺失：** `FAILED` 状态定义 + 重试机制 + 用户提示文案。

---

### 🔴 S1-2 · 图谱页空白时无任何引导

AI 提取结果为 0 个节点时（图片密集型教材、扫描版漏网），用户打开图谱页看到空白 canvas。PRD F4 Done When 只规定"≥10 个节点"的成功标准，未定义低于门槛时的 UI 行为。

**缺失：** Empty State UI + 引导文案（"本次提取未能识别足够节点，建议上传文字版 PDF"）。

---

### 🟡 S1-3 · 第一次看到力导向图没有任何引导

力导向图对多数学生是陌生交互：节点会弹跳，需要点击才能看侧边栏，需要拖拽才能整理布局。PRD 和原型均无新手引导设计，用户可能直接关闭页面。

**缺失：** 最低成本的 onboarding 提示（一行文字："点击节点查看详情，拖拽可重新布局"）。

---

### 🟢 S1-4 · 节点详情"来源页码"是死信息

侧边栏显示"第 12 页"，用户无法从图谱页跳转回 PDF 对应页。页码信息当前无可操作性。

**建议：** 在 PRD Constraints 中明确写入"Phase 1 不支持 PDF 内跳转，来源页码仅供参考"，避免被视为 bug。

---

## Section 2 · 技术风险（5 条）

### 🔴 S2-1 · 批处理编排架构未定义（最严重）

PRD F3/F4 描述"按页分批调用 Claude（每次 3-5 页）"，但未定义谁来串联这 75 批调用（300 页 ÷ 4 页/批）。

- 单 Vercel 函数 for 循环：75 批 × 3s ≈ 225s → **直接超时**
- 前端轮询触发：用户关闭页面即中断
- 后台队列（Supabase Edge Function）：PRD 完全未提及此组件

**缺失：** 批处理编排方案未选型，Issue #4 无对应架构设计任务，开发前必须解决。

---

### 🔴 S2-2 · PDF 上传不应经过 Vercel 函数

PRD F2：`POST /api/documents/upload` 接收文件后上传至 Supabase。  
20MB 文件经 Vercel 函数中转 → 极可能触发 10 秒超时。

**正确架构：** 浏览器直接用 Supabase JS SDK 上传文件（`supabase.storage.upload()`），Vercel 函数只写 `Document` 元数据，不经手文件本体。

---

### 🟡 S2-3 · 20MB 上传限制挡住真实教材

目标用户使用的 200-400 页教材 PDF 实际大小：
- 纯文字教材：10-30MB（边界情况）
- 带插图 CS 教材：20-60MB（大量超限）
- 带彩图理科教材：50-150MB（全部超限）

**缺失：** 20MB 限制来源未在 Constraints 中说明；建议评估是否可提升到 50MB（Supabase 免费层支持单文件 50MB）。

---

### 🟡 S2-4 · Claude API 费用无护栏

300 页教材 × 800 字/页 ≈ 32 万 tokens 输入，claude-sonnet-4-6 约 $1.2-1.5/本。  
50 个早期用户各上传 5 本 → 单月 Claude 费用约 $300-375。无任何配额限制。

**缺失：** 单账号月度上传配额（建议 Phase 1 限制每用户 5 本/月），或成本告警机制。

---

### 🟢 S2-5 · react-force-graph 包体积未声明

`react-force-graph` 压缩后约 200-300KB，在弱网/移动端首次加载明显。

**建议：** 在 PRD Constraints 中注明"Phase 1 不优化移动端加载性能"，避免后续混淆。

---

## Section 3 · PRD 遗漏功能（6 条）

### 🔴 S3-1 · 批处理编排无对应 Issue

当前 10 个 Issue 无任何一个负责"批处理如何编排"。Issue #4 任务清单写"循环调用 Claude API"，但没有架构决策任务。

**建议：** Issue #4 补充任务项"选型并设计批处理编排机制"，或新建 `chore(arch): 批处理编排方案` Issue。

---

### 🔴 S3-2 · 上传后触发方式未决定

PRD F2 原文："上传完成后跳转到处理进度页（**或**触发后台提取任务）"  
"或"是悬而未决的设计分叉，直接影响 Issue #3 和 #4 实现。必须在开始编码前关闭。

**建议：** PRD F2 明确选定方案并删除"或"：
- 方案 A（推荐）：上传完成 → 自动跳转进度页 → 进度页发起提取
- 方案 B：后台静默提取 → 用户可继续浏览 dashboard

---

### 🟡 S3-3 · 没有密码重置功能

F1（Auth）只覆盖注册 + 登录，无"忘记密码"流程。学生忘记密码 = 永久失去所有图谱数据。

**建议：** Issue #2 补充"忘记密码 → 发重置邮件"，或新建独立 Issue。

---

### 🟡 S3-4 · 节点质量无最低门槛

PRD F4 Done When："KnowledgeNode 表新增 ≥ 10 条"，但未定义低于门槛时的行为。提取结果 < 5 个节点时直接展示稀疏图谱，会直接破坏 The Bet 的第一印象。

**建议：** F4 补充：若提取节点数 < 5，`Document.status` 标记 `LOW_QUALITY`，图谱页展示提示而非空图。

---

### 🟡 S3-5 · 重复上传同一文档无检测

同一用户多次上传相同 PDF → 每次触发完整提取流程 → 重复计费 + 重复数据。

**建议：** Issue #3（PDF 文本提取）补充：上传时计算文件 MD5，若同账号下已存在相同指纹则跳转已有图谱并提示。

---

### 🟢 S3-6 · 图谱页数据加载无 Loading 状态

`GET /api/documents/[id]/graph` 可能需要 1-2 秒，当前 PRD 未设计这段时间用户看到的内容。

**建议：** Issue #7（图谱渲染）任务清单补充"数据加载中显示骨架屏或 spinner"。

---

## Section 4 · The Bet 本身的风险（4 条）

### 🟡 S4-1 · 力导向图对学生来说可能是"瞬间困惑"而非"瞬间理解"

The Bet 的核心词是"看到图谱的**瞬间**"，但学生习惯的工具（目录、XMind、PPT 大纲）都是线性或树状，位置固定。力导向图节点弹跳、布局不确定，第一眼感受可能是困惑。

PRD 没有设计任何帮助用户"学会读图谱"的引导，这是 The Bet 的执行断层。

**建议：** Phase 1 上线后监控"图谱页平均停留时长"，若 < 30 秒则视为 Bet 存在问题，需要加引导或改布局策略。

---

### 🟡 S4-2 · 竞品 NotebookLM 未在 PRD 中承认

Google NotebookLM 已提供文档上传 + AI 问答，免费且稳定。NeuronMap 的唯一差异化是知识图谱可视化。PRD 没有正面回应这个竞品。

**建议：** PRD 补充竞品分析段落，明确"图谱质量是我们的生死线"，并将此作为 Claude 提示词优化的核心目标。

---

### 🟢 S4-3 · "自动生成"不等于"比手动更有用"

认知科学角度：手动整理知识图谱的过程本身是学习（主动回忆 + 整合）。AI 自动生成跳过了这个过程，学生看到的是"AI 的理解"而不是"自己的理解"。

**建议：** Phase 1 收集用户反馈，问一个问题："看完图谱后你对这本书的理解有没有变化？"用定性反馈验证这条假设。

---

### 🟢 S4-4 · The Bet 没有验证计划

PRD 有 The Bet 但无测量方式，无法知道假设是否成立。

**建议：** PRD 补充 3 个核心行为指标（可用 Vercel Analytics 或日志统计）：
1. 图谱页平均停留时长（目标：> 2 分钟）
2. 打开图谱后发起 AI 问答的比例（目标：> 40%）
3. 7 天内上传第二本书的用户比例（目标：> 20%）
