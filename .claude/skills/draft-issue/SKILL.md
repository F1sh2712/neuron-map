# /draft-issue

## 这个 skill 做什么

读取用户提供的 PRD 文本或需求描述，输出一个格式规范、验收标准可被机器/人工验证的 GitHub Issue 草稿。

输出结果可以直接复制粘贴到 GitHub，或由用户确认后用 `gh issue create` 提交。

---

## 输入

用户提供以下任意一种：
- PRD 中的某个功能章节（Feature Spec）
- 一段自然语言需求描述
- 一句话功能需求（此时必须先反问，见下文"何时反问"）

---

## 输出格式（严格遵守，不得增减章节）

```
**Title:** feat(<module>): <动词 + 名词短语，≤ 50 字>

**Labels:** type: feat | module: <模块> | scope: <frontend/backend/db/infra> | p<0/1/2>: <级别>

---

## 背景

<2-4 句话。说明为什么需要这个功能，以及它在整个产品流程中的位置。
只引用 PRD 中已有的信息，不添加假设。>

## 用户故事

> 作为<具体用户角色>，我希望<做什么操作>，这样<获得什么价值>。

（一个 Issue 只允许一个用户故事。）

## 任务清单

- [ ] <具体可执行的开发任务，粒度：一个工程师半天内可完成一条>
- [ ] ...

（任务清单描述 What to build，不描述 How，不超过 8 条。）

## 验收标准

- <具体的、可验证的条件。必须包含以下至少一种证据形式：>
  - HTTP 响应码（如 `→ 返回 201`）
  - 数据库字段值（如 `Document.status 变为 COMPLETED`）
  - 可测量的数字（如 `< 200ms`、`≥ 10 条记录`）
  - 文件存在性（如 `Supabase Storage 中可见该文件`）
  - UI 状态变化（如 `按钮从 disabled 变为可点击`）
- ...

**依赖：** <填写前置 Issue 编号，如"Issue #4 完成后"，若无则填"无">
```

---

## 必须遵守的规则

### R1 · 只用 PRD 里有的信息
不得在 Issue 中添加 PRD 未提及的功能、字段、接口或交互。  
如果你认为某个细节是"显然需要的"，**不要自行添加**，在输出末尾用 `❓ 待确认` 标注，等用户决定。

### R2 · 验收标准必须可自动或人工核查
每条验收标准必须能回答"怎么证明它做完了"。  
禁止出现无法核查的验收标准，例如：
- ❌ "功能正常工作"
- ❌ "用户体验良好"
- ❌ "代码质量高"
- ✅ "`POST /api/xxx` 返回 `201`，响应体包含 `{ id, email }`"

### R3 · 一个 Issue 只服务一个用户故事
如果需求描述包含多个独立用户目标，**拆成多个 Issue 草稿**，分别输出，不合并。

### R4 · 信息不足时先反问，不要猜
如果输入缺少以下任何一项，停止输出草稿，改为提问：
- 功能的触发条件（谁触发？什么情况下？）
- 成功/失败的预期结果
- 涉及哪个数据模型或 API 路由
- 优先级（p0 / p1 / p2）

反问格式：
```
在输出 Issue 之前，我需要确认以下几点：
1. ...
2. ...
请回答后我再生成草稿。
```

### R5 · 依赖关系必须显式标注
如果该 Issue 的开发需要另一个 Issue 先完成，必须在"依赖"字段注明，不得留空或忽略。

---

## 反模式 — 遇到以下情况，拒绝输出并说明原因

| 反模式 | 拒绝理由 |
|---|---|
| 输入只有"实现登录功能"等空洞描述 | 缺少触发条件、成功标准、涉及模型，无法生成可验证的 Issue。触发 R4 反问。 |
| 一段需求包含多个用户角色（如"管理员可以…，学生可以…"） | 违反 R3，拆成独立 Issue 分别输出。 |
| 验收标准含"提升性能""优化体验""更快""更好"等模糊语言 | 违反 R2，必须量化（如"响应时间 < 500ms"）或改写为可观测状态。 |
| 需求中要求"支持所有文件类型" | PRD Phase 1 明确只支持 PDF，此类描述与 PRD 冲突，拒绝并引用 PRD 原文。 |
| 用户要求在一个 Issue 里同时覆盖前端和后端的完整功能链 | 工作量过大，建议拆分为独立的 frontend / backend Issue，分别打 scope label。 |
| 任务清单条目包含"写好代码""保证质量"等非行动项 | 删除或要求用户改写为具体文件/接口/组件名称。 |

## 示例

**输入：**
```
根据 PRD F2，帮我草拟 PDF 上传的 Issue。
```

**输出：**

```
**Title:** feat(upload): PDF 文件上传至 Supabase Storage

**Labels:** type: feat | module: upload | scope: frontend, backend | p0: blocking

---

## 背景

用户上传 PDF 是整个知识图谱流程的起点。文件存入 Supabase Storage `documents` bucket，
元数据写入 `Document` 表，并触发后续 AI 提取流程。

**依赖：** Issue #2 (Auth) 完成后方可开发（需要 userId）

## 用户故事

> 作为小林，我希望拖拽或点选一份 PDF 教材上传，这样系统能帮我自动提取知识图谱。

## 任务清单

- [ ] 创建上传页 `/dashboard/upload`：拖拽区域 + 文件选择按钮
- [ ] 前端校验：仅允许 `.pdf`，大小 ≤ 20MB
- [ ] `POST /api/documents/upload`：接收文件，上传至 Supabase `documents` bucket
- [ ] 上传成功后写入 `Document` 表 `{ userId, filename, fileUrl, status: 'PENDING' }`
- [ ] 上传完成后跳转到进度页

## 验收标准

- 上传合法 PDF → Supabase Storage `documents/` 目录可见文件，`Document` 表新增 1 条记录，`fileUrl` 非空
- 上传非 PDF 文件 → 客户端提示"仅支持 PDF 格式"，Network 面板无请求发出
- 上传 > 20MB → 客户端提示"不能超过 20MB"，Network 面板无请求发出
- 未登录调用 `POST /api/documents/upload` → 返回 `401`

**依赖：** Issue #2 (Auth) 完成后方可开发
```

```

```
